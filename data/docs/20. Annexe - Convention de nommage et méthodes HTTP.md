# Annexe - Convention de nommage et méthodes HTTP

Cette annexe est la convention de référence pour nommer les fichiers d'une application SAND. Les exemples sont des noms de fichiers, de classes et de fonctions tirés de l'application SIHAM-HEBERGES-APP.

## 1. Pourquoi une convention

Le nom d'un fichier doit dire deux choses :

- **qui y a accès** : le premier segment désigne le Guard (le contrôle d'accès de `Session`) ;
- **ce qu'il fait** : l'objet manipulé, puis l'opération.

Quand on lit `admin-user-list`, on sait sans ouvrir le fichier que seul un administrateur y accède, qu'il s'agit des utilisateurs et que la page les liste.

## 2. Les pages

Une page est formée de trois fichiers qui portent **le même nom en kebab-case** :

| Rôle | Emplacement |
|------|-------------|
| Modèle (métadonnées) | `application/include/modeles/<page>.model` |
| Contrôleur | `application/include/controlleurs/<page>.php` |
| Vue | `application/include/vues/view/<page>.blade.php` (ou `<page>.html.twig`) |

Le nom se lit ainsi : `<guard>-<objet>-<opération>`.

- Le **premier segment est le Guard** : `admin-` implique `Session::checkACL_admin()`, et ainsi de suite pour les autres profils (`wifi-`, `vpn-`, `heberge-`).
- Vient ensuite **l'objet**, puis **l'opération** (`list`, `add`, `create`, `search`, `results`...).
- Les **pages publiques n'ont pas de préfixe**.

Exemples :

| Page | Lecture du nom |
|------|----------------|
| `admin-user-list` | Guard admin, objet user, liste |
| `admin-organisme-add` | Guard admin, objet organisme, ajout |
| `heberge-create-from-individu` | Guard heberge, création à partir d'un individu |
| `heberge-search-individu-name-results` | Guard heberge, résultats de la recherche d'un individu par nom |
| `vpn-create` | Guard vpn, création |
| `wifi-individu-etat-civil` | Guard wifi, objet individu, état civil |
| `index` | page publique d'accueil |
| `cgu` | page publique |
| `error-access-denied` | page publique d'erreur (accès refusé) |

Le contrôle du Guard se fait dans le contrôleur de la page, par exemple :

```php
\SAND\Object\Session::createAndTestSession();
\SAND\Object\Session::checkACL_admin();
```

Le premier segment d'un nom de page est un préfixe de Guard. Le tableau suivant en donne la liste :

| Préfixe | Méthode de Guard |
|---------|------------------|
| `admin-` | `Session::checkACL_admin()` |
| `heberge-` | `Session::checkACL_heberges()` |
| `vpn-` | `Session::checkACL_vpn()` |
| `wifi-` | `Session::checkACL_wifi()` |

Règle : **la liste des préfixes de Guard est fermée** et correspond exactement aux méthodes `checkACL_*` de `Session`. Un nouveau Guard ajoute une méthode, puis son préfixe. Dans un nouveau projet, la méthode porte le nom exact du préfixe (`heberge-` → `checkACL_heberge`) ; le pluriel de `checkACL_heberges` est un écart propre à SIHAM.

## 3. Les traitements (POST + PRG)

Un traitement reçoit un formulaire en POST, écrit, puis redirige (Post-Redirect-Get).

Le motif d'un traitement est `<guard>-<verbe>-<objet>`, alors que celui d'une page est `<guard>-<objet>-<opération>`. Les verbes (`create`, `update`, `print`, `send`...) ne sont **jamais** des préfixes de Guard : `create-heberge` est un traitement sans Guard, pas un fichier du Guard `create`.

- Avec Guard : `application/traitements/<guard>-<verbe>-<objet>.php`, par exemple `admin-user-add` ou `admin-freeze-individu`.
- Sans Guard : `<verbe>-<objet>.php`, par exemple `create-heberge`, `send-feedback`, ou les impressions `print-...` (`print-heberge-list-xlsx`).

Chaque traitement :

1. commence par `Session::createAndTestSession()` ;
2. fait ensuite le contrôle du Guard (`Session::checkACL_admin()` pour `admin-...`) ;
3. se termine par une redirection suivie de `die();`.

```php
<?php
\SAND\Object\Session::createAndTestSession();
\SAND\Object\Session::checkACL_admin();

// ... écriture en base ...

header('location: ' . \SAND\Classe\Url::link_rewrite(false, 'admin-user-list', []));
die();
```

## 4. Les actions

Une action est un gabarit appelé par une fonction depuis un gabarit mère. Elle peut interroger la base dynamiquement (voir « 04. Les Actions dans les vues »).

- Classe : `application/include/actions/<Objet>Action.php`, qui étend `SAND\Classe\Implement\Action`.
- Méthodes : `render<Quoi>()`.
- Gabarit : `application/include/vues/view/action-<objet>-<quoi>.blade.php`.

Exemple : `OrganismeAction::renderSelect()` rend le gabarit `action-organisme-select`.

Appel depuis un gabarit mère : la partie avant le point donne la classe (`organisme` → `OrganismeAction`), la partie après le point donne la méthode.

Blade :

```php
<?php echo \SAND\Classe\ControlleurAction::inserer('organisme.renderSelect', []); ?>
```

Twig (fonction `action`, qui appelle la même méthode `inserer`) :

```twig
{{ action('organisme.renderSelect', []) }}
```

## 5. Les conduits AJAX

**Norme applicative : les conduits sont réservés aux appels AJAX.** Un conduit ne sert jamais à afficher une page, ni à traiter un formulaire envoyé de façon classique (POST + PRG, voir les traitements). Une page passe par son contrôleur, un formulaire par son traitement, et seul un appel AJAX (requête `fetch`/`axios`/`XMLHttpRequest` qui attend un fragment HTML ou du JSON) passe par un conduit. C'est ce que fait l'application de référence : son seul conduit, `AjaxConduit`, ne répond qu'à des appels AJAX.

**Quel mécanisme pour un appel AJAX ?** Un appel qui vient des pages du site lui-même passe par un **conduit**. Un appel d'un **client externe** (autre application, script, service tiers) passe par l'API `api/` (voir le §7 et « 18. API wp-json et Ereferer »).

**Écart historique :** les conduits `DocConduit` et `IndexConduit` du squelette rendent des pages entières. C'est un écart à la norme ci-dessus, hérité de l'ancien squelette : ne pas le reproduire dans une nouvelle application.

- Classe : `application/include/conduits/<Type>Conduit.php` (par exemple `AjaxConduit`).
- Gabarits : `application/include/vues/view/ajax-conduit-<...>.blade.php` (par exemple `ajax-conduit-organisme-select-options`).
- **Le conduit contrôle lui-même la session et le Guard** : chaque méthode commence par `Session::createAndTestSession()` puis le `checkACL_...` voulu. Il n'y a pas de contrôleur de page pour le faire à sa place.

## 6. Les vues

```
application/include/vues/
├── view/     gabarits des pages, des actions et des conduits
├── layout/   gabarits mères (body, body-nomenu)
├── system/   gabarit système (system)
└── cache/    généré
```

- Priorités de résolution : `view` 300, `layout` 200, `system` 100 (de la plus forte à la plus faible).
- Layouts : `body`, `body-nomenu` et `system`.
- Quand l'application a plusieurs interfaces (WEB, MOBILE...), on crée **une arborescence par interface**.
- Le dossier `cache/` est généré par le framework ; il n'est **jamais versionné** (à placer dans `.gitignore`).

## 7. Les méthodes HTTP

- **GET** pour lire.
- **POST + PRG** pour écrire.
- **Pas de PUT, DELETE ni PATCH** hors API REST.

Raison : en HTTP/1.1, ces verbes provoquent trop d'erreurs sur le Web : les formulaires HTML sont limités à GET et POST, et des proxys ou des pare-feu les filtrent. GET et POST sont plus sûrs, au prix d'un peu de performance. Une API REST, dont les clients maîtrisent leur chaîne réseau, reste le seul endroit où ils sont admis.

Il existe **deux mécanismes REST**, et PUT, DELETE et PATCH ne sont admis que dans l'un ou l'autre :

- **`api/`** (`SAND\Api\Controller\<espace>\<Ressource>`, avec des actions `getItems`, `getItem`, `createItem`, `updateItem`, `deleteItem`) : c'est le mécanisme **recommandé pour un client externe**. Voir « 18. API wp-json et Ereferer ».
- **`*RestReponse`** : le mécanisme **historique** de SAND, conservé pour les applications existantes.

Le `Controlleur` MVC accepte techniquement PUT et DELETE (comportement préexistant), mais la convention les réserve à l'API : une page ou un traitement ne les utilise pas.

**Exception de nommage de `api/` :** les segments d'espace de noms `v1` et `wp\v2` sont en minuscules, alignés sur les URL `wp-json` (`/wp-json/v1/...`, `/wp-json/wp/v2/...`), contrairement au reste du code (PSR-1, `StudlyCaps`).

## 8. Récapitulatif

| Type de fichier | Dossier | Motif de nom | Exemple |
|-----------------|---------|--------------|---------|
| Modèle | `include/modeles/` | `<guard>-<objet>-<opération>.model` | `admin-user-list.model` |
| Contrôleur | `include/controlleurs/` | `<guard>-<objet>-<opération>.php` | `vpn-create.php` |
| Vue | `include/vues/view/` | `<page>.blade.php` | `cgu.blade.php` |
| Traitement avec Guard | `traitements/` | `<guard>-<verbe>-<objet>.php` | `admin-user-add.php` |
| Traitement sans Guard | `traitements/` | `<verbe>-<objet>.php` | `send-feedback.php` |
| Action (classe) | `include/actions/` | `<Objet>Action.php` | `OrganismeAction.php` |
| Action (gabarit) | `include/vues/view/` | `action-<objet>-<quoi>.blade.php` | `action-organisme-select.blade.php` |
| Conduit (classe) | `include/conduits/` | `<Type>Conduit.php` | `AjaxConduit.php` (réservé aux appels AJAX) |
| Conduit (gabarit) | `include/vues/view/` | `ajax-conduit-<...>.blade.php` | `ajax-conduit-organisme-select-options.blade.php` |
| API REST (contrôleur) | `api/controller/<espace>/` | `SAND\Api\Controller\<espace>\<Ressource>`, actions `getItems`... | `api/controller/v1/Ereferer.php` (espaces `v1`, `wp\v2` en minuscules) |
| Layout | `include/vues/layout/` | `body*.blade.php` | `body-nomenu.blade.php` |
| Système | `include/vues/system/` | `system.blade.php` | `system.blade.php` |
